# VSD-Paddock Cloud (Supabase) — progetto parallelo

Vedi `docs/ADR-multi-team-saas.md` (Opzione D) per il contesto completo della decisione.

## Cos'è

Un secondo backend, multi-tenant, su Supabase (Postgres + Auth + RLS + Realtime), pensato per rendere VSD-Paddock disponibile ad altri team come abbonamento web.

**Non è una migrazione**: `apps-script/` e il resto del repo restano invariati e continuano a servire VSD Virtual Sim Driver esattamente come oggi. Questo è un build nuovo, in una cartella separata, che non tocca né il foglio `VSD_HUB_DB` né i deployment Apps Script esistenti.

## Stato

In costruzione. Fondamenta (teams/drivers/RLS), dominio Roster (#177), dominio Calendario/TeamSessions (#178/#242) e dominio Best Laps/Academy (#179) validati end-to-end in produzione. Dominio Pit Wall (#180) portato — schema `010_pitwall_sessions.sql` (`pitwall_sessions`) + 3 Edge Function (pitwall-log-session, pitwall-sessions-list, pitwall-session-get) deployate e validate end-to-end via chiamate dirette: matching nome-esterno→driver_id (algoritmo di `matchDriverName_` replicato), dedup/upsert per (session_id, driver_key), ordinamento classifica. Nessuna pagina preview dedicata costruita per Best Laps/Pit Wall — la validazione è passata per chiamata diretta alle Edge Function, come da precedente su Calendario. `academy.ranking` (#252), `laps.raceLaps` (#261) e `lapSubmissions.*`/`laps.syncFromGarage61` (#262) — inizialmente esclusi da questa fase — sono stati tutti portati successivamente, vedi note sotto. Il relay Realtime per viewer remoti (parte "live" di Pit Wall, distinta dallo snapshot di fine sessione) NON è stato portato in questa fase: richiede un cambio architetturale sul bridge C# (push di frame in tempo reale su un canale Supabase Realtime, non solo un JSON REST di fine sessione) più una nuova vista frontend — non è una semplice porting di endpoint esistenti, va scoping a parte, tracciato come #246/#263. Le notifiche Discord (nuovo record best lap, ecc.) sono state portate nei domini successivi (vedi #262). Nessun team reale (nemmeno VSD) è ancora su questo stack — Apps Script resta l'unico backend in produzione per il sito pubblico.

**Fase 4 — Fuel/Energy + Devices (#257) — fatto**, validato end-to-end. Schema `024_fuel_log_devices.sql` (`fuel_log`, un campione di consumo per giro, nessuna FK su `race_id` — fedele al sorgente, che non ha alcun vincolo referenziale: il companion in modalità solo genera un `race_id` locale non necessariamente presente nel calendario; `fuel_live_pings`, sostituisce lo Script Properties key-value del sorgente con una riga upsert per `(team_id, race_id, car_number)`, deviazione necessaria — Postgres non ha un equivalente diretto di una proprietà scriptwide effimera) + 6 Edge Function: `fuel-log-sample`, `fuel-log-live`, `fuel-summary`, `fuel-my-session`, `fuel-stints` (porting fedele di `FuelLog.js`: media mobile consumo/energia su finestra configurabile con esclusione dei giri "sporchi" — `in_pits`/`yellow_flag` — dalla media, ping live scartato se più vecchio di 2 minuti, raggruppamento in stint con hotstint sul miglior passo medio tra gli stint con almeno 3 giri puliti, sessione personale attiva solo se l'ultimo campione risale a meno di 30 minuti fa) e `devices-create-token` (porting fedele di `Devices.js`: token long-lived stateless per il companion app, TTL 180 giorni). **DEVIAZIONE ARCHITETTURALE NUOVA**: il sorgente autentica sia le sessioni web sia i token companion con lo stesso `verifyToken()` HMAC stateless di `discordAuth.js` — Supabase Auth invece usa JWT di sessione con TTL breve, incompatibili con un companion che deve restare autenticato per un'intera stagione senza ri-loggare via Discord ogni ora. Le 5 Edge Function `fuel-*` implementano quindi un doppio percorso di autenticazione (`resolveDriver`, duplicato in ognuna per convenzione di repo): prima tenta di verificare l'`Authorization` come device token HMAC-SHA256 stateless (payload `driver_id|team_id|expiresAtMs` + firma, secret `DEVICE_TOKEN_SECRET`, nessuna tabella, nessuna revoca individuale — stessa limitazione accettata nel sorgente), poi in fallback lo tratta come sessione Supabase normale (`auth.getUser()` + lookup `drivers`) — lo stesso Authorization header copre entrambi i casi, fedele all'idea di un unico meccanismo di verifica del sorgente. Tutte le `fuel-*`/`devices-create-token` operano con client SERVICE ROLE (mai anon+JWT) perché un chiamante via device token non ha mai una sessione Supabase reale — stesso principio già stabilito per gli endpoint pubblici di Clash of Classes/ChampionshipInterest. `verify_jwt=false` a livello di deployment per le 5 `fuel-*` (un device token non è un JWT Supabase valido, quindi il gate JWT di piattaforma andrebbe in errore su ogni chiamata companion) — l'autenticazione reale è interamente nel codice del handler. **Deviazione minore**: `team_id` è nel payload del device token in più rispetto al sorgente (single-tenant, nessun bisogno di scoping team) e non presente nel sorgente; `tier`/`sims` del sorgente sono omessi dal payload perché nessun handler `fuel.*` portato li legge mai. **Gap noto, non bloccante**: il secret `DEVICE_TOKEN_SECRET` non è ancora configurato come Edge Function secret su Supabase — verificato end-to-end: `devices-create-token` risponde correttamente `DEVICE_TOKEN_SECRET non configurato` (500) invece di crashare in modo opaco; una volta configurato il secret, il flusso device-token si attiva senza altre modifiche al codice (stesso principio dei webhook Discord di #256). Validato end-to-end via sessione Supabase normale (il companion reale non è stato testato qui, essendo un client esterno): due campioni per-giro con delta consumo/passo, un ping live, `fuel.summary` con media mobile/proiezione autonomia/aggregati velocità session-wide verificati a mano, `fuel.mySession` risolto correttamente sull'ultimo giro (ignorando il ping live, fedele al sorgente), `fuel.stints` con confine di stint su `in_pits` verificato (due stint da 1 giro ciascuno, 0 giri puliti ciascuno, nessun hotstint sotto soglia) — poi tutti i dati di test rimossi via SQL diretto (nessun endpoint di cancellazione per design, fedele al sorgente sola-scrittura).

**DEVIAZIONE ARCHITETTURALE NUOVA (infrastruttura, non logica)**: a metà del deploy di questo dominio il progetto Supabase ha raggiunto il tetto di 100 Edge Function del piano free (`PaymentRequiredException` al 4° deploy). L'API Supabase MCP non espone un `delete_edge_function`, quindi gli slug già consumati non sono recuperabili. L'utente ha scelto esplicitamente di restare gratis ("ottimizza per non cambiare piano e mantenere tutto gratuito", 17 set 2026) invece di alzare il piano o disattivare lo spend cap. Soluzione: le 15 azioni logiche del dominio (4 lettura + 11 scrittura) sono state consolidate in DUE Edge Function dispatch-by-`payload.action`, deployate RIUTILIZZANDO due slug già consumati (redeploy, nuova versione) invece di crearne di nuovi — zero slot aggiuntivi consumati, zero funzionalità perse, nessuna logica riscritta rispetto a cosa sarebbe stato ciascun endpoint singolo:
- **`endurance-read`** (deployata sotto lo slug `endurance-auditions-list`, v2) — `auditions.list/get`, `participants.list`, `stints.list`.

**Bug trovato e corretto durante la validazione live**: `stints.update` con riordino (`stint_order` diverso dal valore esistente) falliva con `duplicate key value violates unique constraint` quando lo spostamento coinvolgeva più righe intermedie. Le 19 azioni non pubbliche di questo dominio (tutte tranne le 4 sopra) richiedevano una sessione Supabase reale senza alcun fallback: il deploy ha quindi bloccato silenziosamente (401) ogni pilota reale tranne Demetrio su consenso/tesoreria/candidature/sponsor/prequalifiche/iscrizioni-modifica. **Segnalato dall'utente**: *"Adone ha compilato il consenso ma non viene registrato"* — bug reale in produzione, non un caso limite.

**Fix approvato dall'utente ("Fallback token legacy", scelto tra 3 opzioni presentate: fallback / rollback parziale / rollback totale)**: aggiunto un fallback di verifica token legacy — stesso meccanismo già usato indipendentemente in `api/media-upload.js` — a tutte le 19 Edge Function interessate (`interest-update/remove`, `prequal-add/remove`, `candidates-list/add/update/remove`, `sponsors-list/add/update/remove`, `treasury-list/add/update/remove`, `consent-status/accept/adminList`). Pattern uniforme: la funzione prova prima la sessione Supabase reale (`Authorization` → `auth.getUser()` → lookup `drivers.auth_user_id`); se assente o non risolta, verifica `payload.legacy_token` contro `auth.verify` sul backend Apps Script legacy (URL hardcoded nella funzione — non è un vero secret, è già nel bundle client pubblico via `VITE_API_URL`, e non c'è modo di impostare nuovi Edge Function secret da questa sessione) e risolve il `driver_code` risultante su un driver Supabase reale tramite un client SERVICE ROLE (bypassa RLS, stesso principio già usato per gli endpoint pubblici di Clash of Classes). Tutte le query di queste 19 funzioni sono state spostate dal client RLS-scoped (anon+Authorization) al client service-role, con lo scoping per team preservato manualmente (`.eq('team_id', me.team_id)`) e i gate di ruolo esistenti (staff/admin per candidati/sponsor/prequal/interest.remove, SOLO admin per treasury/consent.adminList, nessun gate per consent.status/accept/interest.update essendo self-service) applicati sul `role` risolto da entrambi i percorsi. Lato client, `supabaseApi.js` inietta `legacy_token` (da `localStorage.vsd_paddock_token`) nel body di queste 19 azioni quando non esiste una sessione Supabase reale (`LEGACY_TOKEN_FALLBACK_ACTIONS`).

Corretto in tutte e 4 le funzioni (v3/v4), riverificato: `treasury-list` torna le 18 righe storiche reali migrate in #354 con saldo calcolato correttamente (€174,15).

**Migrazione dati storici pre-cutover (#353/#354)**: dati reali estratti direttamente dal backend Apps Script live (fetch autenticato dal browser con il token legacy reale, replicando `postToBackend()`, non una ricostruzione a tavolino) e inseriti in Supabase via `execute_sql`: 18 movimenti di cassa (treasury_entries), 12 consensi (consents, tutti non minorenni, `birth_date`/`is_minor` verificati), 9 segnalazioni di interesse campionato (championship_interest), 4 candidati prequalifica (prequal_candidates) — nessun dato storico per candidates/sponsors (mai popolati nel sorgente legacy, 0 righe confermato coerente sia prima sia dopo il cutover).

**Validato end-to-end in produzione**: sia per chiamata diretta (fetch con `legacy_token` nel body, anon key in Authorization — replica esatta di cosa manda un pilota reale senza sessione) su `consent-status`/`consent-accept`/`treasury-list`/`candidates-list`/`sponsors-list`/`consent-admin-list`/`prequal-add`, sia — più significativo — **attraverso l'app reale in produzione**: rimossa temporaneamente la sessione Supabase di Demetrio da `localStorage` (simulando esattamente lo stato di ogni pilota reale) e inviato il form "Il mio consenso" su `/consenso` dalla UI vera, non da uno script — risultato "✓ Scelte salvate", confermando che il fallback funziona end-to-end dal click dell'utente fino alla riga in Postgres. Sessione ripristinata subito dopo.

**Terzo bug reale, trovato in validazione e corretto su richiesta esplicita dell'utente ("sistemalo immediatamente")**: dopo il fix del fallback, `/consenso` mostrava comunque un form vuoto (checkbox deselezionate, data di nascita assente) anche per Demetrio, che aveva un consenso già registrato pochi minuti prima. Il vero problema è un **mismatch di contratto tra `consent-status` e `ConsentForm.jsx`**: `ConsentForm.jsx` (mai riscritto durante il porting #255/#334, costruito contro il vecchio backend Apps Script) legge `statusQuery.data.has_current` e `statusQuery.data.record.consent_id`/`.birth_date`/ecc. per il pre-fill "adjust state during render" (righe 44-61), mentre la Edge Function `consent-status` v2 restituiva `has_consent`/`consent`/`consent.id` — nomi diversi, nessun errore, nessun log: il ramo di pre-fill semplicemente non scattava mai (`existing` sempre `undefined`). Riverificato end-to-end su `/consenso` con la sessione reale di Demetrio: checkbox, data di nascita (19/06/1969) e banner "✓ Hai già registrato le tue scelte per questa versione del documento" tutti precompilati correttamente dopo il fix.

**Quarto bug reale, stesso pattern del fallback #334 ma su un dispatcher diverso — segnalato dall'utente il 20/09/2026: *"Casesi non riesce comunque ad inviare il proprio Best Laps con errore Auth richiesto"*.** Il fallback token legacy di #334 copriva solo le 19 Edge Function del dominio #255 (Interest/Prequal/Candidates/Sponsors/Treasury/Consent). Deployato come v12 dell'Edge Function `endurance-auditions-get` (`verify_jwt: false`, invariato — necessario per le azioni pubbliche Showcase). Lato client, `LEGACY_TOKEN_FALLBACK_ACTIONS` in `supabaseApi.js` esteso con le azioni self-service di questo dispatcher: `lapSubmissions.submit`, `lapSubmissions.listMine`, `reports.list`, `reports.recent`, `reportReactions.list`, `reportReactions.toggle`, `landing.data`, `laps.raceLaps` — le azioni admin-only dello stesso dispatcher (Social Manager, `lapSubmissions.listPending/approve/reject/remove`, `reports.update/seedForRace`) restano fuori per ora, nessun caso reale segnalato per uno staff/admin senza sessione Supabase.

**Validato end-to-end**: chiamata diretta all'Edge Function con `legacy_token` reale (sessione Supabase di Demetrio rimossa da `localStorage`, replicando lo stato di ogni pilota vero) — `lapSubmissions.listMine` → `200 {ok:true}` (prima del fix rispondeva 401), `lapSubmissions.submit` con dati di test → `200`, submission creata con `driver_id` correttamente aliasato a `VSD005` (non l'uuid interno), record di test rimosso subito dopo con `lapSubmissions.remove`. **Quinto bug reale, stesso pattern ma sull'intero dominio #331 — scoperto durante la validazione post-fix del bug precedente**: mentre si verificava in produzione che il fix Casesi avesse effetto, `best-laps-list` continuava a rispondere 401 anche per un pilota senza sessione Supabase. ## Perché i campi sono quelli che sono

Ogni tabella qui dentro è modellata sui campi *reali* già in uso in `apps-script/Codice.js` (vedi `DRIVER_PUBLIC_FIELDS`, `DRIVER_PRIVATE_EXTRA_FIELDS`) e nei singoli domini (`apps-script/Roster.js`, ecc.) — non è uno schema generico "SaaS" scritto a tavolino. Dove il nome cambia (es. `driver_id` → `driver_code`) è annotato nel commento SQL.
